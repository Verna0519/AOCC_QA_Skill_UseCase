# AOCCQA-fsd-parser（需求分析報告，單一整併 skill）

隸屬 Agent:`AOCCQA-testcase-requirements-analyst`(需求拆解員)，Phase A。把 QA 提供的任何形式規格資料，解析成一份**給 PM/Planner 閱讀**的測試需求分析報告（HTML）。此 skill 一體包含「解析分析」與「HTML 報告產出」，無需其他 skill 搭配。

核心價值：忠實反映規格最終版本、清楚區分「已定義／需釐清／邏輯矛盾」、並讓 PM 能直接複製釐清問題去對答。此 skill 是需求分析，不是 Test Case 明細；若使用者接著要 Test Case，屬後續階段另行處理。

**通用性**：與「哪個產品／哪份文件」無關；流程與輸出結構固定；所有專有名詞**一律從當前這份文件抓取**，不沿用其他文件或本 skill 任何範例詞彙（範例僅示意寫法，不是固定清單）。

## 步驟一：取得並判定規格最終版本（最重要）

1. **優先用 Confluence 連結，而非匯出的 PDF/純文字。** 用 `AOCCPM_confluence-mcp:confluence_get_content`（頁面 ID 取自 URL `/pages/{id}/`，`expand=body.storage,version,space`）取 **storage 原始碼**。PDF/純文字會遺失刪除線與紅字等語意。Jira 附件（二進位）抓不到，改用上傳檔或貼上文字。
2. **判定最終版本：刪除線與修訂標記都要處理。** 刪除線 `<s>`＝舊版作廢，以其後內容為準。此外**顏色標記文字（紅字／magenta）、「Revision Notes／修訂／補充／[補充]」等註記，通常代表對前文的修訂或新增**；與前文矛盾時以修訂為最終規則，並列出被取代的前文供對照。**沒有刪除線不代表沒有版本變更**，仍要掃描這些修訂標記。
3. **inline 註解要讀；頁面一般 comment（footer）不採用為規格。** 用 `confluence_get_comments`（`expand=body.view,extensions.inlineProperties,extensions.location`）取 `location=inline` 的註解，逐則判讀：
   - **採用為澄清**：對規格做補充/修正 → 反映到分析。
   - **已解決（移除）**：標「要拿掉」且本文已無該句 → 視為不存在，不立項、不列缺口。
   - **升級為缺口**：未錨定（markerRef/originalSelection 空）或與本文矛盾且無法判定 → 列缺口/矛盾。
   - footer 問答討論不得當規格依據（即使看似結論）。
   - **工具逾時／無回應時**：重試一次；仍失敗則以本文為主完成分析，於 Source Manifest 標「inline 註解未取得（工具無回應）」並列為已知限制，**不因此中斷報告產出**。
4. **需要看截圖時，先盤點附件。** 用 `confluence_get_attachments` 取清單，比對本文實際引用（`<ri:attachment>`）的檔名，只採用**當前版本引用中的**截圖；忽略孤立/舊草稿附件。（下載工具通常只支援文字類附件，PNG 無法直接取像；若有同頁匯出 PDF，可從 PDF 抽圖檢視。）
5. **圖文一致性比對（必做）。** 逐項把「畫面」與「內文規格」對照，只要對不上就列缺口或矛盾（附「截圖顯示 X／內文寫 Y」）。常見不一致：彈窗/按鈕**文案**不同；截圖有內文**沒提到**的元素（或反之）；示範**資料**對不上（數量、單位、分隔符號、價格）；內文只說「參考截圖」卻**未在圖上標註** → 屬缺口，不可自行從圖推定。方向性：**內文最終版為主、截圖為輔**，衝突不自行裁決。
6. **外部設計連結（Figma 等）視為一份來源。** 登錄 Source Manifest；能用設計工具讀取就讀、據以做 UI 圖文比對；讀不到標「未讀來源」，並提醒**像素／互動級 UI 細節須回 Figma 核對**，Figma 與本文不一致時列缺口/矛盾。
7. **版本比對只在必要時做，且定點做。** 刪除線＋修訂標記＋inline 通常已足以判定最終版本；有疑慮才拉前一版做**單段**比對，不做整頁 diff。

## 步驟二：分析紀律

- **逐份來源、可追溯。** 多份資料先逐份單獨讀完、各自標範圍再整合；每條結論回指來源與位置。建立 Source Manifest（Type/Name/版本或最後更新/Location/Read Status），無法讀取標 `Unreadable`。
- **原子化理解。** 複合陳述拆成一個個可獨立驗證的需求後再分析，避免一句包多規則導致漏驗。
- **不自行補寫規格。** 明確區分：已定義／依上下文合理推論（標「推論」）／尚未定義需 PM/RD 確認。絕不把推論或暫定假設當已確認。
- **矛盾只列不裁決。** 前後打架時列雙方原文與來源，放「邏輯不對之處」，由 PM 決定。
- **不因畫面出現某欄位就推定它是新增或有顯示條件。** 沒寫的就是缺口。
- **Fidelity Check。** 分析完逐項比對原文：(a) 規則/條件/欄位都有對應、沒漏；(b) 沒出現原文沒寫、也無依據的內容；(c) 技術值與原文逐字一致。核對中發現的遺漏/矛盾直接成為待釐清或邏輯項目。

## 步驟三：用 HTML 範本產出報告

讀 `references/report-template.html` 取得完整 HTML/CSS 骨架與各區塊寫法，替換內容後輸出到 `/mnt/user-data/outputs/`，以 `present_files` 呈現。**固定六段、固定順序**：測試目的 → 測試目標 → 測試範圍 → 測試規劃 → 待釐清 → 邏輯不對之處（永遠最後）。

### 標題與版號（Header）

- **標題固定＝來源文件標題**：Confluence 用頁面標題；上傳檔案用文件標題或檔名；多來源用主文件標題。`<title>` 與 H1 一致。
- 標題下只放一行：`產生時間` ＋ `文件版號`，**不放對象、不放其他說明文字**。
  - **Confluence**：版本號＋該版本最後更新內文時間與日期（含時區）。若文件本身另有 Reversion／Version History 表，以文件自身版本號為「文件版號」、Confluence 更新時間為「最後更新」，或並列標明。
  - **非 Confluence（PDF/Excel/貼上）**：用文件自身版本／最後修改日期；取不到標「版本：來源未提供」，不可捏造。
  - 範例格式（僅示意）：`產生時間：YYYY/MM/DD ｜ 文件版號：<來源版本>（最後更新：<時間>）`

### 用語規則

- **固定名詞照來源文件原文呈現、不翻譯、不改寫**（欄位名、狀態值與 enum、型態名稱、價格/費用類型、功能/頁面/按鈕/彈窗名、系統欄位、代號、計算式或符號、API 參數、error code、Job/排程名等），以 `<code>` 呈現，且一律取自**當前這份文件**。
- 句子本身用**白話中文**讓 PM 讀得懂，但固定名詞維持文件原文（不限英文）。

### 各區塊寫法

- **測試目的**：1–2 句，點出要驗證的功能與「前台／後台／DB／Log 一致性」。
- **測試目標**：逐項 `.goal` 卡片。**新增功能**加 `新增` 標籤、**既有機制不加**；每項附一句**驗證頁面／路徑**（依文件寫明確）。
- **測試範圍**：兩欄 `包含 / 不包含`。「不包含」明列程式內部實作、與本次無關的效能/安全/自動化。
- **測試規劃**：**依功能分類**，每功能一個 `.plan` 區塊，含功能名、標籤（`新增` 或既有留白；`可直接測`／`需協助備料`）、一句**簡短「需測原因」**。末尾可放「時機提醒」。
- **待釐清**：每項 `.qa` 卡片，順序：① 主題標籤＋確認對象（`PM`／`RD`）② `原文段落`（逐字擷取，`.src`）③「看不懂的點」白話說明 ④「**需 PM 釐清：**」一句，可直接複製。
- **邏輯不對之處**（`.bugs`，最後）：規格**本身前後矛盾**處（含圖文不一致）。每項：標籤 → 附**雙方原文** → 說明哪裡打架 → 「**需 PM 確認：**」一句（可複製）。與「待釐清」差別：待釐清是「沒寫」，邏輯不對是「寫了但自相矛盾」。

### 標籤規則

- `新增`：本次新增功能（藍底）；既有機制不標。
- 主題標籤（灰底）：一詞概括主題，**依當前文件內容命名**（示例：顯示欄位、站點範圍、比價規則、排程時間…；非固定清單）。
- 確認對象：`PM`（琥珀，業務規則）／`RD`（紫，實作/系統行為）；兩者相關就都標。
- 狀態（測試規劃用）：`可直接測`（綠）／`需協助備料`（紫）。

## 釐清問題撰寫規則

每個問題內含：背景、已知條件、具體情境/數值範例、尚未定義的判斷、想確認什麼、影響哪些測項、確認對象，並附一句可直接複製發送的白話問句，保留所有關鍵條件，不為簡短刪關鍵條件。
**只有同時符合以下才列為正式問題**：① 現有資料沒有完整答案 ② 不是純 RD 內部實作 ③ 屬本次測試範圍 ④ 會影響測試資料/Steps/Expected Result/Pass-Fail ⑤ 不能透過其他正式來源確認 ⑥ 不是既有測項或補強建議的改寫。**例外**：Expected Behavior 被標 `Pending`/`Missing` 者一律強制產生問題。排序只用「Conflict 最高優先、其餘不分級」。

## QA 驗證範圍分類

| 分類 | 定義 |
|---|---|
| **QA Must Verify** | QA 可直接觀察、直接判定 Pass/Fail（UI、金額數量、前後台/DB 一致、Job 後結果、Audit Log、錯誤訊息、狀態流轉） |
| **QA Verify with Support** | 屬 QA 責任但需先請 PM/RD 準備條件（特殊組合、特定狀態、手動觸發 Job、模擬 API 失敗/逾時、多 Customer Group、逾期假資料、DB/Log） |
| **Not Primary QA Scope** | RD 內部實作、不影響功能結果判斷（Class/SQL/Transaction/Scheduler Lock/效能） |

## 空值與 Assumption 規則

`N/A`＝已確認不適用；`Unknown`＝理論應提供但無法辨識；`Pending`＝已辨識為必須確認、尚未取得；空白＝僅選填欄位且確定無內容；不得混用。不得自行建立業務假設當正式需求；QA 明確要求「先依此假設繼續」才可標 `Assumption` 並記錄提出者/日期/影響/風險，PM/RD 確認後才改 Confirmed。

## 產出前自我檢查

1. 標題是否＝來源文件標題；版號是否依來源類型正確取得（取不到標來源未提供，未捏造）。
2. 專有名詞是否全取自當前文件、無沿用其他文件；刪除線/修訂標記是否已判讀；inline 註解是否逐則歸位（取不到是否揭露）；footer 是否未被當規格。
3. 六段是否齊全、順序正確、邏輯不對之處在最後。
4. 固定名詞是否全保留文件原文（未翻譯）。
5. 測試目標是否標驗證路徑、新增功能加標籤、既有未加。
6. 測試規劃是否依功能分類且每項有簡短需測原因。
7. 待釐清/邏輯每項是否都附原文段落、結尾有可複製問句；Pending/Missing 是否都已強制轉問題。
8. 是否已做圖文一致性比對，圖文對不上處已列缺口/矛盾；Figma 等外部來源是否揭露讀取狀態。
9. 是否只列矛盾未替 PM 裁決；未自行補寫規格；推論/假設未被當已確認。
