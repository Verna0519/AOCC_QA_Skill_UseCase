# AOCCQA-fsd-parser v1.3.4（需求分析報告，單一整併 skill）

> 版號僅用於**顯示與報告標示**；skill 識別碼固定為 `aoccqa-fsd-parser`（`name` 欄位不帶版號，以免升版後觸發失效）。實際版號一律讀 frontmatter `metadata.version`。

Agent `AOCCQA-testcase-requirements-analyst`，Phase A。任何形式規格資料 → 給 PM/Planner 讀的需求分析報告（HTML），解析＋產出一體。

價值：忠實反映最終版本、區分「已定義／沒寫／自相矛盾」、依**對測項影響度**分級、PM 可直接複製問句。非 Test Case 明細（後續階段）。專有名詞**一律取自當前這份文件**，不沿用其他文件或本 skill 範例。

## 步驟一：取得並判定規格最終版本（最重要）

1. **優先 Confluence 連結，非匯出 PDF/純文字**（PDF 遺失刪除線與紅字語意）。`AOCCPM_confluence-mcp:confluence_get_content`，頁面 ID 取自 URL `pageId=` 或 `/pages/{id}/`，`expand=body.storage,version,space` → 取 storage 原始碼。Jira 附件（二進位）抓不到 → 改用上傳檔或貼上文字。
2. **最終版本判定：刪除線＋修訂標記都要處理。** `<s>`＝舊版作廢，以其後為準。紅字/magenta、「Revision Notes／修訂／補充／[補充]／[M/D更新]」＝對前文的修訂或新增；與前文矛盾時以修訂為準，並列出被取代的前文供對照。**沒有刪除線不代表沒有版本變更**，仍須掃修訂標記。
3. **inline 註解要讀；footer 一般 comment 不得當規格依據**（即使看似結論）。`confluence_get_comments`，`expand=body.view,extensions.inlineProperties,extensions.location`，取 `location=inline` 逐則判讀：
   - 補充/修正規格 → 採用為澄清。
   - 標「要拿掉」且本文已無該句 → 視為不存在，不立項。
   - 未錨定（markerRef/originalSelection 空）或與本文矛盾無法判定 → 升級為缺漏/衝突。
   - 工具逾時/無回應 → 重試一次；仍失敗則以本文完成分析，Source Manifest 標「inline 註解未取得」列為已知限制，**不中斷報告產出**。
4. **要看截圖先盤點附件。** `confluence_get_attachments` 取清單，比對本文 `<ri:attachment>` 實際引用；只採用當前版本引用中的截圖，忽略孤立/舊草稿（報告的資料來源限制須說明忽略幾張）。PNG 無法直接取像；同頁若有匯出 PDF 可從中抽圖。
5. **圖文一致性比對（必做）。** 畫面 vs 內文逐項對照，對不上就列缺漏或衝突（附「截圖顯示 X／內文寫 Y」）。常見：文案不同、截圖有內文沒提的元素（或反之）、示範資料不符（數量/單位/分隔符/價格）、內文只說「參考截圖」卻未在圖上標註 → 缺漏，不可自行從圖推定。**內文最終版為主、截圖為輔；衝突不自行裁決。**
6. **Figma 等外部設計連結＝一份來源。** 登錄 Source Manifest；讀得到就據以做 UI 比對，讀不到標「未讀來源」並提醒像素/互動級細節須回 Figma 核對；與本文不一致 → 列缺漏/衝突。
7. **版本比對只在必要時定點做。** 刪除線＋修訂標記＋inline 通常已足；有疑慮才拉前一版做單段比對，不做整頁 diff。

## 步驟二：分析紀律

- **逐份來源、可追溯。** 多份資料先各自讀完標範圍再整合；每條結論回指來源與位置。建 Source Manifest（Type/Name/版本或最後更新/Location/Read Status），讀不到標 `Unreadable`。
- **原子化。** 複合陳述拆成可獨立驗證的需求再分析，避免一句包多規則漏驗。
- **不自行補寫規格。** 明確區分：已定義／依上下文推論（標「推論」）／尚未定義需 PM/RD 確認。絕不把推論或暫定假設當已確認。
- **矛盾只列不裁決。** 列雙方原文與來源，放「規格衝突」，由 PM 決定。
- **不因畫面出現某欄位就推定它是新增或有顯示條件。** 沒寫＝缺漏。
- **交叉引用必查。** 文件寫「見 XX／公式見 YY」→ 回頭確認該項目是否真的存在。指到不存在＝缺漏（缺說明）或衝突（標號指錯），依情況歸段。
- **Fidelity Check。** 完稿逐項比對原文：(a) 規則/條件/欄位無漏；(b) 無原文沒寫又無依據的內容；(c) 技術值逐字一致。發現的遺漏/矛盾直接成為缺漏或衝突項。

## 步驟三：用 HTML 範本產出報告

讀 `references/report-template.html` 取骨架 → 替換內容 → 輸出 `/mnt/user-data/outputs/` → `present_files`。

**固定六段、固定順序**（5、6 永遠在最後，不可對調）：

| # | 段名 | 定位 |
|---|---|---|
| 1 | 測試目的 | 驗證什麼、為什麼 |
| 2 | 測試範圍 | 包含／不包含 |
| 3 | 測試目標 | 打到哪幾點、通過長怎樣、驗證路徑 |
| 4 | 測試規劃（依功能分類） | 展開 Test Case 前的骨架 |
| 5 | **規格缺漏**（文件沒寫，需 PM 補寫） | 找不到答案 → 請補充 |
| 6 | **規格衝突**（前後打架，需改掉一邊） | 兩個答案互相矛盾 → 請裁決 |

> 舊名「待釐清／邏輯不對之處」自 v1.3.0 停用。命名須成對，PM 看標題即知要「補寫」還是「裁決」。

### Header

- **標題＝來源文件標題**（Confluence 用頁面標題；上傳檔用文件標題或檔名；多來源用主文件）。`<title>` 與 H1 一致。
- 深色橫幅（深藍底、白標題、底部藍線）；標題下細分隔線後**分別列出四項**（不併成一行）：`抓取資料時間` ／ `文件版號` ／ `最後更新時間` ／ `文件編輯者`。
  - Confluence：版號以文件自身為主、括號註 Confluence 版本（`1.1（Confluence v13）`）；更新時間含時區；編輯者取該版本最後編輯者。
  - 非 Confluence：用文件自身版本／最後修改日／作者。**取不到標「來源未提供」，不可捏造。**
- 橫幅下放狀態 chip（文件狀態、缺漏 N 項含阻擋設計數、衝突 N 項含阻擋設計數）＋六段錨點導覽。
- **報告須標示產生此報告的 skill 版號（兩處）。** 產出時讀 frontmatter `metadata.version` 的**實際值**：(a) Header 標題下方以副標寫出 `AOCCQA-fsd-parser v<實際版號>`；(b) footer 固定寫出 `Generated by AOCCQA-fsd-parser v<實際版號>`（例：當前為 `Generated by AOCCQA-fsd-parser v1.3.4`）——**產出的 HTML 內直接寫死實際版號、不留 `{version}` 佔位符**。輸出 HTML 檔名一併帶實際版號（例：`{來源標題}_需求分析_v1.3.4.html`）。skill 升版後，因每次都重讀 `metadata.version`，新報告自動帶新版號。

### 用語

- **固定名詞照原文、不翻譯、不改寫**（欄位名、狀態值/enum、型態、價格類型、功能/頁面/按鈕/彈窗名、系統欄位、代號、計算式、API 參數、error code、Job 名等），以 `<code>` 呈現，取自當前文件。
- `<code>` **不加背景色**（等寬＋深藍字重即可；背景色留給「加強驗證」標註）。
- 句子白話，名詞維持原文。

### 各段寫法

- **測試目的**：1–2 句，點出功能與前台/後台/DB/Log 一致性；必要時補一句背景。
- **測試範圍**：兩欄。「不包含」明列程式內部實作、無關的效能/安全/自動化、Scope 外站台、既有他案計算本身、外部 API 內部實作、無排程。
- **測試目標**：每卡三段式 —— ①要驗證什麼（一句白話）②**通過：**（寫得出 Pass 判準）③驗證路徑。受缺漏影響者右上角加 `見缺漏 N` 灰標。
- **測試規劃**：依功能分類，每功能一卡：序號、功能名、**標籤置右上**、「要涵蓋：…／需協助：…」。末尾放「資料來源限制」提醒。

### 驗證路徑取用規則

- FSD 明文寫出 → **照錄並標出處**（`驗證路徑（FSD 2.1 明文）：…`）。
- FSD 沒寫 → 只依章節結構做定位描述，註明「FSD 未給路徑，依 X.X 章節定位」。
- **一律不臆造具體選單層級。** 每張測試目標卡都要有驗證路徑，缺者標來源未提供，不可省略。

### 第 5／6 段：認定與寫法

兩段開頭各一個 **Accordion「這一段收什麼？」**，含認定條件、處理方式、與另一段的差別。

**第 5 段 規格缺漏 — 認定（任一）**：① 完全沒提此情境或數值；② 有提到但沒定義判準（如只說「達門檻」沒說用哪個數字比）；③ 引用了某項目但文件中找不到；④ 只寫正常情況，例外/邊界沒交代。
→ PM **補寫**即可，原敘述不必更動；問句用「請補充」語氣。

**第 6 段 規格衝突 — 認定（任一）**：① 兩處對同一件事給出相反結論；② 兩條規則觸發條件會同時成立卻要求不同結果、未定優先序；③ 同一東西用了兩種名稱；④ 章節編號或交叉引用指到不存在/錯誤位置。
→ PM 需**裁決以哪邊為準並修改另一邊**，不能只用補充說明帶過。

**卡片結構**
- 第 5 段：標題（點出缺什麼）＋影響度標籤（右上）→ `問題點：` 一行 → `FSD 原文對照`（Accordion）→ `📋 要問 PM 的`（可直接複製）。
- 第 6 段：**標題本身即「需裁決的問題」**（例：「A 與 B 同時成立時，以哪一條為準？」）＋影響度標籤（右上）→ `問題點：` 用 **A vs B 對照句**一行 → `FSD 原文對照`（Accordion）→ `🔧 建議修正`。**不放**「要問 PM 的」，**不另設衝突點方框**。
- 共通精簡原則：只保留「問題點一行 → 原文（收合）→ 焦點問句」。**不寫敘事鋪陳、不重複解釋影響度**（右上標籤已表明）。

**FSD 原文對照（兩段共用）**
- Accordion；摘要列直接寫**出處路徑**（`FSD 原文對照｜3.2 Checkout Page › 1) 區塊 › [項目]`）。
- 展開後先寫章節標題路徑，再逐條照錄原文，**保留文件自身編號與條列層級**（`1.2`、`2.1`、`1)`、`・`、`-`）；**不翻譯、不改寫、不摘要**。
- 字級小於內文、行距收窄、條目間不加分隔線。
- 衝突項把**互相打架的兩條規則並列同一區塊**。
- 章節路徑做成可點擊深連結 → 見下。

### 原文回連規則（Confluence 來源）

- Header 四項後加 `來源頁面`，連 `{base}/pages/viewpage.action?pageId={id}`（永遠有效，保底）。
- 每行章節標題路徑（`.qh`）做錨點：`{base}/spaces/{SPACE}/pages/{id}/{title-with-plus}#{PageTitleNoSpaces}-{HeadingTextNoSpaces}`。兩段皆移除空白後以 `-` 相接；非 ASCII 與 `[ ] ( ) /` 做 percent-encode。標題文字**先還原 HTML 實體再編碼**（`&amp;` → `&` → `%26`），直接拿 `&amp;` 編碼必定定位失敗。
- **錨點後追加 text fragment，精準高亮出問題的那一句**：`#{錨點}:~:text={引用文字}`。Chrome／Edge 完整支援，命中即自動滾動並高亮，讀者無需自行 Ctrl+F；命中失敗時瀏覽器自動退回錨點，兩者互為保底。
  - 引用文字**必須逐字取自 storage 原文**：不改寫、不補字、不跨越省略、不修正錯字。改寫過必定命中失敗。
  - 長段落用範圍式 `text={起始片段},{結束片段}`，兩片段須各自逐字存在。
  - **內文中的 `-` `,` `&` 在 text fragment 語法裡有特殊意義，必須額外編碼為 `%2D` `%2C` `%26`。** 一般 URL 編碼函式不處理 `-`，這是最常漏的一項。
  - 片段取全頁唯一、約 6～15 字者；過短會命中到錯誤位置。
- **錨點只能到真標題**：先掃 storage 的 `<h1>~<h6>` 確認。表格列／清單項沒有錨點 → 錨點連最近上層標題，**再用 text fragment 指向該列實際文字**（text fragment 對表格內文字同樣有效，這正是純錨點做不到的部分）。僅當該處文字無法形成唯一片段時，才於 footer 註明「此處錨點僅到標題層級，請於該標題下方檢視」。
- 掃標題時**順便核對報告引用的章節名與實際標題文字一致**（如報告寫 `1. Overview`、實際是 `1. 需求說明`）。不一致以實際標題為準修正。
- 連結一律 `target="_blank" rel="noopener"`；**維持 hyperlink 外觀**——藍字（`#2f6fb0`）＋點線底線（`1px dotted #a9c3de`）＋尾端 `<span class="ext">↗</span>`，即樣板的 `.qh` 樣式，不搶焦點。
- **不得把原文回連改成 button／chip／方框或任何按鈕化樣式。** 第 5／6 段「FSD 原文對照」的既有版面一律沿用，不因新增回連或 text fragment 而改版：加錨點與 text fragment **只加長 `href`**，不動元素結構、`class`、內文與樣式。
- 非 Confluence 來源不做錨點與 text fragment，只在 Source Manifest 標檔名與頁碼/工作表位置。

### 影響度分級（第 5／6 段共用）

Accordion 呈現判定準則，三層各自可展開、預設收合。標籤置卡片**右上角**。

| 層級 | 認定（任一） |
|---|---|
| `高優先權｜阻擋設計`（紅） | ① 不知道答案就寫不出預期結果，測項無法設計或執行；② 會動到已上線功能，弄錯可能讓原本正常的功能壞掉；③ 牽涉金額怎麼算／能折多少／擋不擋得住，做錯會算錯錢；④ 兩處講法相反且沒說聽哪邊 |
| `次優先｜影響精度`（琥珀） | ① 可先用合理假設寫下去，假設錯要重工；② 影響邊界數值或提示文字，主流程照樣測；③ 較少人走到的路徑或次要情境 |
| `可稍後｜不影響判定`（灰） | ① 答案是什麼都不改變過或不過，只影響文件可讀性；② 可邊測邊問，不卡案例設計 |

- 同層排序：影響金額或會員權益 > 使用者多常走到 > 與需求核心關聯度 > 影響測項數。
- 卡片由高往低排序，序號重新連號。
- 影響度**只用右上標籤**表達，不另寫「為什麼是 X 優先權」。
- 回覆後可能升級者（如引用指向外部文件且公式不同），註明升級條件。

### 視覺規則（避免顏色/線條誤讀）

- **段落識別色 → 只用在頂端標頭橫幅**（淡色底＋色塊編號＋標題）。
- **卡片左側色條 → 全文件只代表影響度**（紅/琥珀/灰），不得表示段落歸屬。
- **整段不鋪底色**；底色只用於重點欄位方框（FSD 原文、要問 PM 的、建議修正、資料來源限制、驗證路徑）。
- **文字底色只留一種**（黃底＝加強驗證的重點：邊界規則、判定時機、卡控結果、進位規則等），段首要有圖例。專有名詞不標底色。
- 標籤置卡片右上，顏色與該段標頭色**對比**（藍標頭段落用橘/紫/綠/灰），不同色系。
- 低飽和淺色、少線條，用留白與圓角卡片分層。

### 標籤

`新增` / `既有` / `含既有回歸`；測試規劃狀態 `可直接測` / `需協助備料`；測試目標指回缺漏 `見缺漏 N`（灰）；影響度 `高優先權｜阻擋設計` / `次優先｜影響精度` / `可稍後｜不影響判定`。**第 5／6 段不用 `PM`／`RD` 標籤**（問句已寫明對象）。

## 釐清問題撰寫規則

每題含：背景、已知條件、具體情境/數值範例、尚未定義的判斷、想確認什麼、影響哪些測項，並附一句可直接複製的白話問句；**保留所有關鍵條件，不為求短刪關鍵條件**。
**同時符合以下才列為正式問題**：① 現有資料無完整答案 ② 非純 RD 內部實作 ③ 屬本次測試範圍 ④ 影響測試資料/Steps/Expected Result/Pass-Fail ⑤ 無法透過其他正式來源確認 ⑥ 非既有測項或補強建議的改寫。**例外**：Expected Behavior 標 `Pending`/`Missing` 者強制產生問題。排序依影響度三層由高往低。

## QA 驗證範圍分類

| 分類 | 定義 |
|---|---|
| **QA Must Verify** | 可直接觀察並判 Pass/Fail（UI、金額數量、前後台/DB 一致、Job 後結果、Audit Log、錯誤訊息、狀態流轉） |
| **QA Verify with Support** | 屬 QA 責任但需 PM/RD 先備條件（特殊組合、特定狀態、手動觸發 Job、模擬 API 失敗/逾時、多 Customer Group、逾期假資料、DB/Log） |
| **Not Primary QA Scope** | RD 內部實作、不影響功能結果判斷（Class/SQL/Transaction/Scheduler Lock/效能） |

## 空值與 Assumption 規則

`N/A`＝已確認不適用；`Unknown`＝理論應提供但無法辨識；`Pending`＝已辨識為必須確認、尚未取得；空白＝僅選填欄位且確定無內容。**不得混用。**
**不得自行建立業務假設當正式需求。** 僅當 QA 明確要求「先依此假設繼續」才可標 `Assumption`，並記錄提出者/日期/影響/風險；PM/RD 確認後才改 `Confirmed`。

## 產出前自我檢查

1. 標題＝來源文件標題；Header 四項分列且依來源取得（取不到標來源未提供，**未捏造**）。
2. 專有名詞全取自當前文件；刪除線/修訂標記已判讀；inline 逐則歸位（取不到已揭露）；footer 未當規格。
3. 六段齊全、順序正確；5、6 段用新名稱且在最後。
4. 固定名詞未翻譯；`<code>` 無背景色。
5. 測試目標每張具備「要驗證什麼／通過／驗證路徑」，路徑已標明明文或章節定位。
6. 測試規劃依功能分類；標籤右上且與段落色對比。
7. 5／6 段各有「這一段收什麼？」Accordion，認定條件與兩段差異已寫明。
8. 章節路徑已做錨點**並追加 text fragment**（引用文字逐字取自原文，`-` `,` `&` 已編碼為 `%2D` `%2C` `%26`）；Header 有保底來源頁面連結；引用章節名與 storage 實際標題一致（非真標題連最近上層＋text fragment 指向該列文字）。**連結維持 `.qh` hyperlink 樣式，未被按鈕化，第 5／6 段版面與前版一致。**
9. 5／6 段每項：影響度標籤（右上、無 PM/RD）＋ FSD 原文對照（Accordion、含路徑、保留原編號、未翻譯）；卡片維持「問題點一行 → 原文 → 焦點問句」；第 6 段標題即需裁決的問題，無「要問 PM 的」與衝突點方框。
10. 影響度三層皆有分佈、由高往低、序號連號。
11. 左側色條只代表影響度；識別色只在頂端橫幅；整段未鋪底色；黃底只標加強驗證重點。
12. 圖文比對已做，不符處已列缺漏/衝突；交叉引用已回查；外部來源已揭露讀取狀態。
13. **只列矛盾未替 PM 裁決；未自行補寫規格；推論/假設未當已確認。**
14. 報告 Header 副標與 footer 皆標 `AOCCQA-fsd-parser v<實際版號>`（直接寫死實際版號，不留佔位符），版號＝當前 SKILL.md `metadata.version`；輸出檔名帶同一版號。
